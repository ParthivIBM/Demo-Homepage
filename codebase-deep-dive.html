Codebase Deep-Dive

Every file, every feature, every React pattern — explained in full.

1 · Architecture Overview

The app is a Create React App project using React 19. It has two pages, a shared API layer, and shared layout components. There is no global state manager — data flows top-down through props.

App.js (BrowserRouter) ├── Route "/" → pages/Home.jsx │ ├── Header │ ├── Banner │ ├── ProductList ──→ api.js → fetchProducts() │ │ └── ProductCard (Link to /products/:id) │ └── Footer │ └── Route "/products/:id" → pages/ProductDetail.jsx ├── Header ├── main (all product sections) └── Footer
Data layer: All raw fetch() calls live exclusively in src/api.js. Components never call fetch directly — they import named async functions. This is the standard separation-of-concerns pattern.

2 · File-by-File Breakdown

src/App.js modified
BrowserRouter Routes / Route Client-side routing

What it does

The root of the React tree. It wraps everything in BrowserRouter, which gives every descendant component access to React Router's navigation hooks and context. Inside it declares exactly two routes:

  • path="/" renders Home
  • path="/products/:id" renders ProductDetail, where :id is a dynamic URL segment (e.g. /products/3)

Why BrowserRouter here

BrowserRouter uses the HTML5 History API so URLs look clean (/products/3) rather than hash-based (/#/products/3). It must wrap the entire app exactly once, at the top level — that's why it lives in App.js and not inside any individual page.

src/api.js new
async / await fetch API Named exports Error throwing

What it does

A pure data-access module. It exports two async functions and nothing else:

  • fetchProducts() — calls https://dummyjson.com/products, checks res.ok, and returns the products array directly (not the full response object).
  • fetchProductById(id) — calls https://dummyjson.com/products/{id} and returns the full product object.

Why a separate file

Putting fetch() directly inside a component couples the component to a specific URL and response shape, making it hard to test, reuse, or change later. By isolating it here, any component can call fetchProductById(5) without knowing anything about HTTP. The BASE_URL constant means the API host is only written once.

Error handling pattern

Both functions throw an Error when the HTTP response is not OK (e.g. 404, 500). The calling component catches this in its own try/catch and stores the error message in state, which it then renders as an error message. This keeps error-display logic in the UI layer where it belongs.

src/pages/Home.jsx modified
useState useEffect useRef useLocation URLSearchParams scrollIntoView Lazy state initialiser

What it does

The homepage. It owns the searchQuery string and passes it down to both Header (to display in the input) and ProductList (to filter the grid). It also handles scroll-to-products behaviour.

Lazy state initialiser

useState(() => { ... }) — the function passed to useState runs only once on the initial render. It reads ?search= from the current URL so that if you arrive at /?search=shoes, the search field is pre-filled and the product list is already filtered. Without the lazy initialiser, the state would always start empty.

useLocation + URLSearchParams

useLocation() returns the current URL's location object. location.search is the query string (e.g. ?search=shoes). Wrapping it in new URLSearchParams(location.search).get('search') safely extracts the value. The useEffect that watches location.search re-syncs the state whenever the URL changes — for example when React Router's back/forward is used.

handleSearchChange + useRef (scroll deduplication)

When the user types a search, this function is called on every keystroke. Without the guard, scrollIntoView would fire on every single character, making the page scroll repeatedly while typing. useRef stores the previous submitted query (it persists between renders but doesn't trigger re-renders). The scroll only fires when the new trimmed query is different from what was previously submitted — meaning it triggers exactly once per search action, not once per keystroke.

Mount-time scroll (arriving from ProductDetail)

The second useEffect with [] runs once on mount. If the URL contains ?search= (because the user searched from the ProductDetail page and was navigated here), it scrolls the page to the product list automatically. The setTimeout(..., 50) gives the DOM time to finish rendering before scrolling.

src/pages/ProductDetail.jsx new
useParams useNavigate useState useEffect Async data fetching Controlled image gallery Scroll-to-top Conditional rendering

useParams — reading the URL id

const { id } = useParams() extracts the :id segment from the URL. If the URL is /products/7, then id is the string "7". This value is passed directly to fetchProductById(id).

Scroll-to-top on id change

A dedicated useEffect with [id] as its dependency calls window.scrollTo({ top: 0, behavior: 'instant' }). This fires before the fetch completes, immediately resetting the scroll position when any product link is clicked. 'instant' (not 'smooth') is intentional — a smooth scroll from the middle of a previous product page to the top would look wrong. The scroll happens first, then the data loads.

Data fetching pattern

The fetch useEffect also has [id] as its dependency, so it re-runs whenever a different product is opened (not just on first mount). The inner async function load() pattern is required because useEffect callbacks cannot themselves be async — you define an async function inside and call it immediately. setLoading(true) and setError(null) are reset at the top so stale states from a previous product are cleared before loading begins.

Conditional render guards

Three render exits appear before the main JSX: loading state, error state, and a null guard if product is somehow still falsy after loading. This ensures the destructuring const { title, price, ... } = product only runs when the data is confirmed to exist — no runtime "cannot read property of null" errors.

Image gallery state

activeImage is an integer index into the allImages array. Clicking a thumbnail calls setActiveImage(i), which updates the index and causes React to re-render the main image with the selected source. activeImage is also reset to 0 inside the fetch success handler so switching products always shows the first image.

Original price calculation

The API returns price (discounted) and discountPercentage. The original price is derived by reversing the discount: originalPrice = price / (1 - discountPercentage / 100). This is displayed crossed-out next to the sale price.

Search from ProductDetail

The Header calls onSearchChange on every keystroke AND on Enter/button click. ProductDetail needs to distinguish between the two because typing should only update local state, but submitting should navigate to Home. The handleHeaderSearch function detects submission by comparing the incoming value to searchQuery.trim() — if they are identical (no new character was typed), it means the Enter key or search button was pressed, so it calls navigate('/?search=...'). Otherwise it just updates local state to keep the input controlled.

src/components/Header.jsx modified
useNavigate useCallback Link scrollIntoView Controlled input Anchor interception

Controlled search input

The search <input> has value={searchQuery} and onChange={(e) => onSearchChange(e.target.value)}. This makes it a controlled input — React owns the value, not the DOM. Every keystroke calls the parent's handler, keeping the parent's state in sync with what's displayed.

Three ways to submit a search

  1. Typing: onChange fires on every character, calling onSearchChange with the latest value.
  2. Enter key: onKeyDown fires; if the key is 'Enter', it calls onSearchChange(e.target.value.trim()) — trimmed so leading/trailing spaces are removed.
  3. Search button click: onClick calls onSearchChange(searchQuery.trim()) using the current state value.

The useCallback around the handleKeyDown function memoises it so it isn't recreated on every render — it only recreates when onSearchChange changes. This prevents unnecessary re-subscriptions to the DOM event listener.

Nav links — Link vs anchor

All nav links are React Router <Link> components rather than plain <a> tags. This means clicking them does a client-side navigation — no full-page reload, no flash, the React tree stays alive. Only the URL and the matching route's component change.

handleAnchorClick — anchor interception

The anchorMap maps two virtual paths to real element IDs:

  • '/#products' → element with id="products" (the ProductList section)
  • '/#footer' → element with id="footer" (the Footer)

When one of these links is clicked, e.preventDefault() stops the default Link navigation, then document.getElementById(targetId) finds the DOM node. If it exists (user is already on Home), scrollIntoView({ behavior: 'smooth' }) scrolls to it. If it doesn't exist (user is on ProductDetail), navigate('/') goes to Home first, then a setTimeout of 100ms gives React time to mount the home components before scrolling. Links without an entry in anchorMap (e.g. '/' for Home) fall through the early return and behave as normal client-side links.

src/components/ProductList.jsx modified
useEffect (fetch on mount) useState Client-side filtering Client-side sorting IIFE pattern

Data fetching

Fetches once on mount via useEffect(load, []). The empty dependency array means the effect runs only when the component first mounts — not on every re-render. It calls fetchProducts() from api.js and stores the result in products state.

Three-state loading pattern

loading, error, and products are three separate state values. The finally block in the try/catch always sets loading to false regardless of whether the fetch succeeded or failed, ensuring the loading spinner is always dismissed.

Search filtering

searchQuery is lowercased and trimmed, then each product title is tested with .includes(query). If the query is empty, the full product array is used. This is entirely client-side — the API is only called once; all filtering happens in memory.

Tab sorting (IIFE pattern)

An immediately-invoked function expression (() => { ... })() computes the final display array based on the active tab. It creates a shallow copy with [...filteredProducts] before sorting — Array.sort() mutates in place, so spreading first protects the original order for the "Latest Products" tab. Three modes: sort by rating descending, sort by stock descending, or return the filtered array as-is.

src/components/ProductCard.jsx modified
Link wrapper CSS link reset Lazy image loading toFixed() Array.from star rendering

Link wrapper

The entire card is wrapped in <Link to={`/products/${id}`}>. React Router's Link renders an <a> tag under the hood but intercepts the click to perform client-side navigation. The CSS class .product-card__link applies display: block; text-decoration: none; color: inherit to remove all default anchor styling so the card looks exactly as it did before — no blue underlines or color changes.

StarRating component

Array.from({ length: 5 }, (_, i) => ...) creates an array of exactly 5 elements and maps each to a star span. The index i is compared to Math.round(rating) — stars below the rounded value get the star--filled class (orange), the rest stay grey. The rating number is displayed as rating.toFixed(1) — always one decimal place.

Lazy loading

loading="lazy" on the <img> is a native browser attribute that defers loading the image until it is about to scroll into the viewport. With potentially 30 product images on screen, this significantly reduces initial page load bandwidth.

src/components/Footer.jsx modified
id="footer" scroll target Controlled form input e.preventDefault()

Scroll target

id="footer" was added to the root <footer> element. This is the DOM node that Header's handleAnchorClick targets when "About" or "Contact" is clicked.

Newsletter form

The email <input> is a controlled input — its value is bound to the email state. handleSubscribe calls e.preventDefault() to stop the form from triggering a full-page GET/POST request (the default browser behaviour for form submission), then resets email to '', clearing the input.

3 · Cross-Cutting Feature Flows

Flow A — Clicking a product card

1. User clicks a ProductCard 2. <Link to="/products/7"> fires a client-side navigation 3. BrowserRouter updates the URL to /products/7 4. React Router matches Route path="/products/:id" → mounts ProductDetail 5. useEffect([id]) fires immediately → window.scrollTo top 6. useEffect([id]) fires → fetchProductById("7") called 7. Loading state shown (Header + "Loading product…" + Footer) 8. API responds → setProduct(data), setLoading(false) 9. Full product page renders with all 7 sections

Flow B — Searching from the Homepage

1. User types "mascara" into Header search input 2. Header onChange → onSearchChange("mascara") (every keystroke) 3. Home.handleSearchChange sets searchQuery = "mascara" 4. First call with a new value → scrollIntoView("#products") fires 5. ProductList receives searchQuery="mascara" as prop 6. filteredProducts = products.filter(p => title includes "mascara") 7. Grid re-renders showing only matching products 8. User presses Enter → Header onKeyDown → onSearchChange("mascara") 9. Same trimmed value → handleSearchChange detects no change, no extra scroll

Flow C — Searching from ProductDetail

1. User types "shoes" in Header search input on ProductDetail page 2. Header onChange → handleHeaderSearch("shoes") — new value → setSearchQuery 3. User presses Enter → Header onKeyDown → handleHeaderSearch("shoes") 4. trimmed ("shoes") === searchQuery.trim() ("shoes") AND non-empty 5. → handleSearchSubmit fires → navigate("/?search=shoes") 6. BrowserRouter navigates to / 7. Home mounts with location.search = "?search=shoes" 8. Lazy initialiser reads "shoes" → searchQuery starts pre-filled 9. Mount-time useEffect([]) detects ?search → scrollIntoView("#products") after 50ms 10. ProductList filters to "shoes" products immediately

Flow D — Clicking "Products" / "About" / "Contact" from any page

Scenario 1: Already on Home Click → handleAnchorClick → getElementById("products" or "footer") found → scrollIntoView({ behavior: "smooth" }) Scenario 2: On ProductDetail Click → handleAnchorClick → getElementById not found (element not in DOM) → navigate("/") → Home mounts → setTimeout 100ms → getElementById found → scrollIntoView({ behavior: "smooth" })

4 · React Hooks Reference

useStateStores a value that, when changed, causes the component to re-render. Used for searchQuery, products, loading, error, activeImage, email.
useEffectRuns side-effects after render. Dependency array controls when it re-runs: [] = once on mount, [id] = whenever id changes, [location.search] = whenever the URL query string changes.
useRefStores a mutable value that persists across renders without triggering re-renders. Used in Home to remember the previous search query so scroll deduplication works.
useCallbackMemoises a function so it keeps the same reference between renders unless its dependencies change. Used in Header for handleKeyDown to avoid creating a new function object every render.
useParamsReact Router hook. Reads dynamic URL segments (e.g. :id) as an object.
useNavigateReact Router hook. Returns a navigate(path) function for programmatic navigation — used to push /?search=query from ProductDetail, and to go to / before a scroll in Header.
useLocationReact Router hook. Returns the current URL's location object (pathname, search, hash, state). Used in Home to read ?search=.
